这份指引帮助接手 agent 从可运行工程出发，逐步构建和迭代新的玩法 Demo。它同时说明三个归档工程可以复用什么、不能据此推断什么。体验要求与验收方法见 [体验设计原则](experience-principles.md)。具体安装结果、资产完整性与远端上传结果，以本次归档的验证记录为准。

## 2. 先恢复工程，再开始新玩法

1. 阅读目标工程新编 README、`package.json`、锁文件、`vite.config.ts`、`scripts/` 和数据库迁移。核对 `app/page.tsx` 实际引用的入口；工程保留的旧组件不一定被当前页面使用。
2. 在新的工作目录或分支恢复。保留来源 commit 和资产哈希；不要在归档副本中直接混入另一个未发布工程。
3. 使用工程记录的 Node/npm 版本与锁文件安装依赖。三个恢复源均声明 Node `>=22.13.0`，并提供 `install:ci`、`dev`、`build`、`typecheck`、`test` 脚本；归档另外新增 `db:init`，用于初始化本地 D1。最低版本声明不等于任意更高版本都已验证，实际复现环境见归档验证记录。
4. 先运行现有检查与构建，记录退出码和首个错误。成功构建后再进行修改，避免把原有环境问题算作新改动的缺陷。
5. 构建后执行 `db:init`，再启动本地服务。新本地 D1 不会自动建表；本次复现中，未迁移时首次 API 请求返回 503。初始化后检查接口返回真实状态，不能只以页面 HTTP 200 判定运行成功。

首次启动按以下顺序，在选定 Demo 目录执行：

```sh
npm run install:ci
npm run typecheck
npm run build
npm run db:init
npm run start
```

`db:init` 对应 `scripts/init-local-db.mjs`：读取构建生成的配置，将迁移目录明确指向该工程的 `drizzle/`，并强制使用 `--local` 应用迁移。Cloudflare 构建配置的默认迁移目录不符合这份归档布局，不能直接执行 `migrations apply DB --config dist/server/wrangler.json` 代替初始化步骤；使用归档提供的 `npm run db:init`。

`npm run start` 使用构建后的 Worker 配置，与初始化脚本共用 `.wrangler/state` 中的本地数据。日常开发可按工程 README 使用 `npm run dev`，但新目录仍需先完成上述数据库初始化。不要把 `.wrangler/`、`node_modules/`、私有环境文件或运行数据打入源码备份。

另行运行 `npm test` 并记录结果。历史套件尚未全绿，不应把启动成功或构建成功写成“所有测试通过”；也不要通过删除失败测试来消除交接限制。

**历史实现**：三个工程采用 React/TypeScript、Three.js 场景、Vite/Vinext 构建以及 Cloudflare Worker/D1 适配。`build/` 中包含构建插件和 Worker 入口源码，不能看到目录名就当成可删产物；`dist/` 是构建结果，不能代替可编辑源码。

## 3. 构建一个新玩法的阶段

以下流程是**建议**。每阶段产物应足以判断下一步，而不是为了凑齐文档。

| 阶段 | 要回答的问题 | 最小产物与进入下一阶段的条件 |
| --- | --- | --- |
| 定义体验 | 用户什么都不做能看到什么？做一次动作改变什么？隔天为什么再来？ | 一页玩法说明：围观、首次参与、重复参与、返回四条路径；列出本轮不做的能力 |
| 选择实现范围 | 是单机演示、多人共享房间，还是需要跨设备长期资产？ | 状态表：每字段的拥有者、保存位置、有效期、可见对象、更新动作 |
| 灰盒闭环 | 去掉精美资产后，核心动作是否成立？ | 用简单几何体完成进入、动作、结果、下一次机会；能演示失败与空状态 |
| 动作与空间 | 分身是否实际走到目标、触碰工具、承接结果？ | 一条完整动作链；相机、碰撞、朝向、道具挂点可验证 |
| 美术与声音 | 美术是否帮助识别状态和空间？ | 通过尺寸、格式、性能与权利检查的资产；加载失败时仍有清楚反馈 |
| 多人和恢复 | 两个客户端竞争同一资源会怎样？断线重试会不会重复结算？ | 权威服务端状态、幂等命令、容量规则、重连方案及关键并发检查 |
| 验收和发布 | 交付状态是否可复现、可回退？ | 实际检查结果、版本映射、资产清单、发布包、回退说明和已知限制 |

不要由已有工具反推产品方案。只需展示空间氛围时，先做小型客户端原型；需要共享结果时再实现服务端规则；需要跨设备收藏时再增加身份和持久化设计。生成式工具主要负责素材供给，不能代替模拟规则、网络同步和数据一致性。

### 核心状态的分工

| 状态类别 | 建议拥有者 | 示例与边界 |
| --- | --- | --- |
| 即时视觉状态 | 客户端 | 粒子、镜头缓动、悬停；不能据此确认库存或占位成功 |
| 交互意图 | 客户端提交，服务端校验 | 点击移动、加入、收取、创作；可先有等待反馈，但结果待服务端确认 |
| 共享结果 | 服务端 | 房间成员、占位、作品、收益、阶段开始时间；所有客户端读取同一事实 |
| 个人偏好 | 本地或账户设置 | 静音、镜头、上次选择；清除浏览器数据后的变化应可解释 |
| 长期资产 | 有版本与迁移的持久存储 | 收藏、进度；需明确是设备会话归属还是账户归属，以及恢复和删除方式 |

## 4. 工具的职责与交付物

下列是本类工程可采用的工具分工。它描述可用能力，不保证每个执行环境都已安装这些工具。

| 工具或能力 | 负责什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 代码 agent、编辑器、Git | 拆解规则、实现与审查、差异记录、版本恢复 | 编译通过不能证明玩法有复访价值 |
| Node/npm 与锁文件 | 可复现的依赖安装、编译、类型检查和测试 | 本机缓存安装成功不能证明全新环境离线可装 |
| React/HTML/CSS | UI、触控入口、弹层、状态与可访问性 | UI 显示成功不能代替服务端结果 |
| Three.js 与 GLB | 3D 场景、骨骼与动作、相机、资源生命周期 | 模型整体摇晃不等于可信的角色动作 |
| Blender/Python 等资产脚本 | 建模、绑定、导出、缩略图与批量校验 | 有导出脚本不代表私人参考图或生成服务都可恢复 |
| 图像/音频生成与编辑能力 | 探索形象、纹理、海报、音乐候选 | 能下载或生成不代表已取得所有再分发权利 |
| ffmpeg/音频分析脚本 | 转码、响度、时长、采样与包体检查 | 数值通过不能证明听感、接缝和节拍标注正确 |
| Worker/API 与 D1 | 权威状态、持久化、校验与多人争用 | 数据库可写不代表客户端实时同步已成立 |
| 浏览器与真机测试 | 检查 WebGL、触控、声音、键盘遮挡、帧率与网络恢复 | 桌面宽屏截图不能替代手机竖屏验证 |
| 托管发布工具与 GitHub | 保存源码、构建包、部署记录、可追溯交付 | 本地 commit 不代表远端上传成功；上传不等于部署 |

需要某项工具时先核对可用能力与现有脚本；不要为复用一个工具而加入无关服务、持久凭据或线上副作用。自动化可以并行处理独立素材，但同一工程的依赖安装、版本切换、资产清单更新和发布由单一负责人协调。

## 5. 资产生成、优化与恢复

**建议流程**：保留输入来源与权利范围 → 在隔离目录生成 → 检查尺寸与动作 → 转换运行格式 → 计算哈希 → 更新清单 → 只安装验收通过的输出。不要直接重跑旧生成脚本覆盖已确认的运行素材。

资产清单至少记录：稳定 ID、文件路径、用途、字节数、SHA-256、格式、生成或转换脚本、来源类别、许可/授权范围和缺失输入。依赖他人服务时注明服务与模型版本；无法确定就记为未知，不能推测。

| 资产 | 运行格式与检查建议 |
| --- | --- |
| 分身与场景模型 | 优先自包含 GLB；核对坐标轴、单位、脚底、面向、骨骼命名、权重、包围盒、贴图引用；角色 ID 与模型路径解耦 |
| 动作 | 核对关节是否真实变形、工具是否在手、脚是否穿地；分别检查待机、移动、工作、反馈与中断 |
| 缩略图与图片 | 按实际显示尺寸导出；保留需要的透明度；使用目标浏览器可解码的压缩格式；不要把原始高分辨率参考图塞入首屏 |
| 声音 | 保留署名与修改说明；记录编码后实际时长和增益；首次播放、静音、后台恢复、循环接缝单独验收 |
| 程序生成物 | 提交生成脚本与必要参数；注明依赖版本；输出可能受 Blender/编码器版本影响，不能承诺跨版本逐字节一致 |

**历史实现**：角色目录与运行时适配器分开维护；当前选择项应从 `lib/club-avatar-catalog.ts` 或 `lib/fishing-avatar-catalog.ts` 读取，不能用旧 README 或目录文件数猜测。生成脚本存在多代历史版本，运行资产的清单与哈希比文件修改时间更可靠。

源资产、第三方原始录音、私人参考图和服务端运行数据可能不在归档中。可编辑源码完整、运行素材完整、生成过程可重现是三个不同结论，应分别检查。历史素材说明中的“已授权用于公开 Demo”不自动等于无限制再分发授权；本次归档也不替代素材原有权利条件。许可未知时明确限制，不把仓库公开可读理解为可任意商用或再许可。

## 6. 多人、时间与持久化

**历史实现**：三个工程都有服务端命令与数据库适配，不能归类为纯静态模拟。云蹦迪通过房间客户端请求快照并发送心跳；云钓鱼和火人节也采用 HTTP 快照刷新。它们使用共享服务端时间与动作状态，再由客户端绘制连续画面。这种多人同步不等同于逐帧 WebSocket 广播。

服务端持有房间版本和个人命令序号；D1 适配中以条件更新协调并发。浏览器保存设备会话能力后可关联服务端记录，不能因此声称账户登录、跨设备同步或长期不丢数据已经具备。本地 Wrangler 数据也不等于线上 D1 数据。

为新玩法设计协议时，建议做到：

1. 用明确的命令描述意图，不允许客户端直接提交最终库存、收益或房间 JSON。
2. 同一次不确定请求重试沿用身份和幂等标识；确认失败后才允许新的业务动作。超时不等于服务端未执行。
3. 用版本号拒绝过期快照；本地预演应有有效期，失败后回到权威结果。
4. 用服务端时间定义阶段和结果窗口。动画可插值，不能以每个客户端私有计时器决定中奖或阶段切换。
5. 为离线、超时、满员、重复提交、旧客户端与数据库不可用分别设计反馈。失败时不要悄悄生成一个本地房间，继续显示“实时”。
6. 将环境 NPC 与真实参与者分开记录和计数。共享的确定性 NPC 表演可以增强氛围，但不能伪装成真人上线。
7. 持久化采用明确版本与迁移。上线前确认数据库备份、回退兼容性和删除范围，不把代码回退当成数据库回退。

## 7. 手机优先与性能预算

**用户明确要求**：手机竖屏优先，操作直达，分身动作有代入感。

下面数值是新 Demo 的**初始建议预算**，不是三个旧版的实测结果，也不是不可调整的验收标准。先确定代表设备、网络条件与满员场景，再用实际测量修订。

| 项目 | 起始目标 | 超出时优先处理 |
| --- | --- | --- |
| 画面稳定性 | 代表中端手机满员场景持续达到 30 fps；目标帧时间不超过约 33 ms | 降低像素比、阴影、后处理与远处细节；再定位骨骼、粒子和绘制开销 |
| 首次可见反馈 | 约 1 秒内出现有意义的加载或基础画面；测试网络下约 5 秒内可开始核心体验 | 拆分关键资源和可延迟资源，避免等待全部角色和全部音频 |
| 首屏传输 | 关键交互资源压缩后优先控制在 5–10 MiB | 延迟加载收藏内容、额外模型与完整音乐；压缩纹理与模型 |
| 角色资产 | 每角色先以约 20–30k 三角形、2–4 个材质绘制批次作为评审起点 | 优先减少重复材质、过细几何和不可见附件；实际看满员总成本 |
| 响应反馈 | 触摸后下一帧出现按下或等待反馈；不将请求延迟隐藏为无响应 | 将反馈与结果确认分开，禁止无意义重复提交 |
| 资源回收 | 连续进入退出与切换分身后内存不持续单向增长 | 清理几何、材质、贴图、音频节点、事件监听与定时器 |

竖屏布局至少覆盖窄屏与常见大屏，考虑底部安全区、地址栏变化、软键盘、横竖屏切换和单手可达性。主动作、倒计时和自己分身不应互相遮挡；加载、断网和满员时仍保持可读。尊重减少动态效果偏好，提供静音与必要的非声音提示。

## 8. 迭代、验收、备份与发布

每次迭代先写一个可验证问题，例如“首次进入者能否不阅读说明完成一次收取”，再选择最小改动。不要一次同时更换玩法、角色、美术、网络和收益规则，否则难以判断变化原因。

建议按以下顺序验收：

1. **工程**：从干净副本安装，执行类型检查、相关测试、构建；验证源码和素材相对路径。
2. **规则**：关键状态转移、容量临界值、重复请求、重连、过期命令、数据库错误；有并发就测试竞争同一名额或作品。
3. **体验**：首次进入、围观、首次动作、重复消费、退出再来、加载失败；手机竖屏检查镜头、动作、触控与声音。
4. **多人**：至少两个独立会话观察同一动作和结果；同时加入、同时提交、离开回收名额、切后台恢复。
5. **长期运行**：经历至少两个完整循环，确认阶段更替、资产释放、计数与个人记录没有累积错误。
6. **交付**：锁定 commit，生成清单与可重复压缩包，记录测试环境、结果、失败项与未执行项；检查上传内容不含敏感材料。

本次仅进行后台 HTTP API 启动验证，未执行第 3 步的浏览器/手机 UI 与现场多人体验验收，不能在交接时补写为通过。三个工程构建成功与历史测试未全绿是两个独立结果；具体失败项以归档验证记录为准。旧测试结果只有在对应 commit 与环境明确时才可引用。
