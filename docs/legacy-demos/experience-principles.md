# 玩法 Demo 的体验设计原则

这份文档区分用户明确提出的方向、三个旧版已有的实现，以及新玩法的建议。它不是声称所有原则都已在旧版完整实现的验收报告。源码定位与实现流程见 [开发指引](development-guide.md)。

## 1. 用户明确要求：空间应当值得待，也值得回来

| 要求 | 设计时要落实的行为 | 验收时怎么判断 |
| --- | --- | --- |
| 不操作也有基础体验 | 进入即可看到空间、角色或环境在活动；围观不被强制表单阻断 | 不点击等待一段时间，仍能看懂这里发生什么，并知道怎样参与 |
| 多人参与影响空间 | 行为能改变别人共同看到的动作、作品、节奏或状态 | 两个独立会话观察同一次行为，能识别相同的共享变化 |
| 持续运行，无整体终点 | 局部事件可结束，空间继续产生下一次机会 | 至少经历两个循环后仍可参与；没有全局“通关后无事可做” |
| 可重复消费与复访价值 | 返回时有值得发现、参与或继续的内容 | 重复三次操作仍有选择或变化；退出再来可说明留下了什么、更新了什么 |
| 分身有真实动作与代入感 | 角色对准目标、移动到位、操纵工具并承接结果 | 看动作即可判断意图；手、脚、道具与结果对应，不能只靠文字说明 |
| 操作直达，减少多余点击 | 主动作在需要时出现；无新信息的中间弹层可以省略 | 从当前状态完成下一步无需重复确认同一选择；失败有直接恢复入口 |
| 手机竖屏优先 | 镜头、主动作和关键状态围绕纵向可视区组织 | 窄屏下能看见自己、目标和主要反馈；软键盘与底部安全区不遮挡操作 |
| 状态与容量一致 | UI、协议和实际规则使用同一语义 | “在线”“可加入”“围观”“已收藏”分别有可核验来源；临界值不互相矛盾 |
| 诚实标注 NPC、本地模拟和实时联机 | 环境角色、示例数字、本地偏好与共享结果可区分 | 断网不继续假装联机；NPC 不计为真人；示例数据有明确说明 |

这些是本次交接确认的方向。未来玩法可与用户重新讨论具体取舍，不能把某一个项目的角色数、周期长度、配色或入口布局提升为永久规则。

## 2. 历史实现：可以借鉴的具体做法

以下结论来自本次核验的三个发布源码 commit，而非本轮浏览器体验。归档副本另有隐私清理，例如用中性占位图替换来源与公开授权不明的个人主页图片；它不是线上源码的逐字节复制。本轮三个工程构建成功，历史测试套件尚未全绿；启动验证限于后台 HTTP API。按用户要求没有打开本机浏览器或桌面，因此视觉、声音、真机性能和跨设备体验仍需后续验收。

### 共享事实与本地演出分开

三个工程包含共享服务端状态、命令校验与 D1 存储适配。客户端读取快照并绘制连续画面；分身动作可以插值，但名额、钓鱼结果和作品状态由服务端确定。火人节连接失败时不会创建一个本地房间替代共享房间。

可借鉴的是“同一结果来源”的分工，不能据此推断已支持任意在线规模、账户系统或跨设备长期资产。

本次恢复也验证了环境初始化会影响体验：新本地 D1 未迁移时，首次 API 返回 503，不能把它显示为已进入共享房间。归档新增 `npm run db:init`，在构建后、本地启动前应用迁移；正确步骤见开发指引。基础页面可显示不等于共享服务已经可用。

### 环境角色不占真人名额

源码分别维护真人参与者与环境角色。云蹦迪有独立环境角色列表；云钓鱼与火人节的快照有 `ambientParticipants` 等独立数据。当前三工程真人容量均写为 10，但云钓鱼还定义了 12 个物理站位；**可见位置数、环境角色数、可加入名额不是同一个数字**。

具体数量是这些版本的选择。新玩法应先定义容量语义，再决定 UI 怎么显示，不能机械沿用“10 人”或从场景里的空位反推可加入人数。

### 有阶段结束，但空间继续

火人节按共享时间经历创作、燃烧、灰烬后进入下一轮。源码保留下一轮状态推进，而不是让整个体验在一次燃烧后结束。云钓鱼将抛竿、等待、咬钩、逃脱或持有、收藏分成状态，收进背包需要对应命令。

可借鉴的是清楚的阶段与下一次机会。燃烧周期、起竿窗口、收藏方式不应不经评估就套给新玩法。

### 分身、资产和呈现状态有契约

当前角色选择项来自角色目录，资源路径和协议 ID 有明确映射。部分旧 ID 有兼容映射，目录中保留的 GLB 不全等于当前可选角色。加载、提交与同步状态在页面和客户端中有处理。

新 agent 应从实际入口和目录核对角色，不根据历史说明、资产数量或印象补写名称。换模型时同时检查脚底、比例、朝向、道具接触点、相机与动作范围；能显示出模型只是第一步。

### 示例 UI 不等于真实产品数据

现有页面中能找到带说明的示例热度、基础点赞值、本地点赞状态，以及统一框架保留的示例资料。它们是原型表达方式，不能据此推断真实社交关系、运营数据或账户体系已实现。新玩法应清理无关示例，并保留必要的事实说明。

## 3. 建议：把原则变成可测试的设计选择

### 先做自然停留，再做主动操作

默认画面可以用环境运动、角色待机与空间事件提供节奏。基础体验不是“所有收益自动发放”：先说明围观能获得什么，参与又多了哪种控制和反馈。没有真人时也能看懂；有真人后，共享变化应当更丰富。

环境伙伴可帮助冷启动，但其行为不应遮挡或抢走真人的核心机会。对可竞争资源，明确 NPC 是否参与、是否消耗名额以及是否可能影响结果。

### 每次操作形成完整的因果链

以“选择目标 → 意图反馈 → 分身执行 → 结果显现 → 下一步”为检查链。用户点下后立即看到响应，但结果只在确认后呈现。角色中途被打断、目标失效或请求超时时，应给出与画面一致的状态。

动作可信度优先看接触关系和时机：手握住工具、脚支撑身体、朝向目标、收获由角色接住。增加粒子、震动和镜头摇晃不能修复动作本身的错位。

### 用变化提供复访理由

先选择一种主要复访理由，例如空间被共同改变、个人收藏积累或可表达的作品。每种理由都说明“回来时能看到什么变化”。不要仅靠更长等待、更高数字或增加随机掉落来声称长期留存价值。

若设计包含离线积累、自动结算或分享快照，应先作为新能力定义上限、时间来源、重复领取和过期规则。这些是新玩法建议，不是本次三个旧版已实现的功能。

### 降低操作成本，同时保留必要选择

默认推荐一种明确动作。只有选项真的改变结果时才要求选择；保存形象后通常回到刚才的任务。退出、重试、静音、返回自己视角应容易找到。

不要以“少点击”为由隐藏高影响选择。涉及不可逆清空、付费或公开发布时，解释具体后果并遵守当次授权；日常可逆体验操作不需要层层确认。

### 在同一视野内连接自己、目标和结果

竖屏里先让用户知道“哪个是我、我能做什么、刚刚发生了什么”。选取跟随、俯视或局部聚焦镜头时，围绕当前任务判断。进入作品聚焦后应有可见返回路径；自动镜头不要与拖动、缩放手势争夺控制。

主要信息应有层级：即时动作反馈靠近动作，持续状态放在稳定区域，说明和次要设置按需展开。避免把容量、网络状态、倒计时和提示堆在同一角落。

### 状态文案必须有确定来源

| 显示给用户的含义 | 所需事实 | 常见误导 |
| --- | --- | --- |
| 在线人数 | 未过期的真人存在状态 | 把 NPC、历史访问量或示例热度算为在线 |
| 已加入 | 服务端确认的参与者身份与有效名额 | 点击按钮后立刻当成加入成功 |
| 已收藏／已结算 | 幂等写入成功且可再次读回 | 仅播放动画或把对象藏起来 |
| 实时共享 | 当前连接和可接受的新快照 | 请求失败后沿用旧“实时”标签 |
| 此设备保留 | 明确的本地或设备会话关联范围 | 暗示换设备也会自动恢复 |
| 空位可用 | 权威容量、预留与成员规则 | 仅看 3D 场景里是否还有空椅子 |

界面可以用通俗语言，但不能省略影响用户判断的事实。技术原因通常留在日志中；用户需要看到当前结果、下一步和是否会重复执行。

## 4. 下一轮体验验收清单

以下是接手者后续要执行的检查，**不是本轮已通过列表**：

- 无操作进入：空间有可理解的活动，加入入口可见，未强制开启声音。
- 首次参与：能够识别自己和目标，完成一次核心动作，动作与结果相符。
- 重复参与：连续操作三次，规则一致；没有卡在结算或必须刷新页面的状态。
- 两人参与：互相能看到共享变化，加入/退出/容量一致；环境角色始终可区分。
- 网络异常：超时后结果不被猜测，重试不重复发放；重连后回到服务端事实。
- 再次返回：个人数据保存范围符合说明；循环已推进时不会回到错误阶段。
- 手机竖屏：窄屏、键盘、安全区、触控手势、相机返回与自己分身均可用。
- 低性能与资源失败：模型或音频失败有恢复方式，满员与多个循环后资源不持续累积。
- 可访问性：静音、减少动态效果、文字对比和非声音关键提示可用。
- 公开说明：NPC、示例数值、本地数据、实时联机和素材权利范围均与实际一致。

记录失败时写清设备、步骤、期望、实际和对应版本；不要只写“体验不好”。把新的决策记录为有适用范围的结论，保留反例和撤销条件，方便下一位 agent 继续迭代。
