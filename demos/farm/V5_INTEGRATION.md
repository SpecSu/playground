# V5 creation and local visitor integration

Audit date: 2026-10-22. This audit read repository source and documentation only. No `.env`, credential values, cookie values, database contents, external API, downloaded script, browser, publication or service operation was used.

**External integration blockers:** a verified generation provider and entitlement/quota policy; stable accounts and friend relations; authenticated owner-to-visitor grants; filtered, versioned estate snapshots; content/rights review; and an explicit publication/Remix distribution service. These are absent from the audited farm integration. This module does not add credential or paid-service requirements. Free-form text is never mapped to a preset while being described as AI generation.

The local implementation uses `pasture`, `lotus` and `starlit` official templates, private captures, and clearly marked **本地访客演示 / 示例庄园**. No real friend, concurrent presence, remote permission, public publishing or AI-generation success is claimed. A future service must replace the local adapter with real authorization; these synthetic actor IDs are not authentication.

## Pure module API

`src/v5/creation.ts` exports serializable state/command/context/effect types, `createCreation(ownerId, profileId)`, `reduceCreation(state, command, context)`, `localVisitView`, `THEME_TEMPLATES`, `LOCAL_VISITORS` and `CREATION_RULES`. `src/v5/creation-estate.ts` implements `applyEstateCreation(profile, ownerId, {command, actor?, capture?}, now)` and exports its `CreationLayoutReceipt` type for the profile's optional `creationLayouts` ledger.

The context is produced by the estate engine: trusted time, owner/actor identity, profile, layout version, current materials, stable animal IDs, hunger, compatible food by animal, current component regions, factual source events, and optionally current camera/thumbnail. Do not take identity, clock, compatible food, event titles or component-region lookup directly from an incoming command.

The reducer owns only creation records. It never changes owner materials, normal growth, bond, memories, positions, risk, or physical layout. All changes are immutable candidates. A successful command carries a local receipt, and replaying its ID produces no effects. Proposal/help IDs also prevent accepting with a new command ID twice. The estate store remains responsible for atomic durable receipts and concurrent requests.

| Commands | Result |
| --- | --- |
| `themePreview {theme}` → `themeApply {draftId}` → `themeUndo` | Preview stays in a draft. Confirmed application/undo emits a versioned `theme` effect. Theme versions increase monotonically; stale previews and repeated undo fail. The scene renderer must show the selected preview and the actual applied theme. |
| `saveWork {title,eventIds?}` | A private capture freezes current scene/theme/profile, animal IDs, camera and optional root-supplied thumbnail. Factual event titles come from trusted `context.sourceEvents`, never fabricated client history. Saving has no publishing effect. |
| `blueprintDraft {scope,baseVersion,budget,components}` → `blueprintApply {draftId}` | Structured allowlisted component differences become an `acceptedBlueprint` plan. No script, animal state, inventory or executable code is accepted as content. |
| `grant {visitorId,regions,budget,editTypes,expiresAt,allowView?,allowHelp?,allowRemix?}` / `revokeGrant` | Owner opt-in local demo permission. View, help, component edits and Remix are distinct. Revoke invalidates pending work and sessions, and refunds reserved help once. There is no publication permission. |
| `enterVisit {mode:'example'}` or `{mode:'local-visitor',grantId}`; `visitMove`, `visitInteract`, `leaveVisit` | Independent route/projection state. Example interactions affect only that visit. `localVisitView` rechecks current authorization and returns only the visit projection; never expose the complete owner `CreationState` to a visitor. |
| `submitHelp {visitId,targetId,food}` / owner `acceptHelp`, `rejectHelp` / `sweep` | Synthetic donor food reserves 1 on submission, consumes once on acceptance, refunds once on rejection/expiry/revoke. Full targets and daily limits remain visibly waiting in the gift basket. |
| `submitProposal {visitId,scope,baseVersion,budget,components}` / owner `acceptProposal {proposalId,componentIds?}`, `rejectProposal`, `undoProposal` | Owner accepts all or a selected nonempty subset; the complete selected plan is sent for fresh validation. Stale versions, expired/revoked grants, invalid scope/type, overspending and duplicate acceptance fail. Undo identifies the exact original transaction, never a whole save rollback. |
| `setProposalRemix {proposalId,allowRemix}` / `remixProposal` | Separate explicit local demo content permission; creates a private component-only draft with version-linked parent attribution. It copies no animal identity, bond, hunger, inventory, camera, photo, event history or private source input. Local demo permission is not a consent record for a real third-party author. |

Component shape: `{id, region, estimatedCost, edit: LayoutEdit}`. `LayoutEdit` is the spatial module's exported union. The creation module reconstructs only allowed fields and checks the declared region against edit coordinates. For existing-object visitor operations, `context.componentRegions` must prove the source region. Full footprints, owned cells, actual current costs, collisions, doors, occupied shelter capacity and legal routes still belong to the spatial validator. An estimate is never a trusted price.

## Root transaction contract

1. Load the authoritative owner/profile state and deduplicate the command in one durable transaction. Local UI simulation may select only the fixed synthetic `LOCAL_VISITORS`; never accept arbitrary remote `actorId` as authorization.
2. Build the trusted creation context and reduce the command. Owner writes are denied for visitor actors. A real external visitor adapter must return only a permitted projection, with fresh authorization on every read and interaction.
3. For `acceptedBlueprint`, resolve actual source and destination footprints, verify every edit is within the current grant/scope, and re-run exact cost, terrain, navigation, occupancy and capacity validation against the current layout. Partial acceptance is a fresh plan, not a splice into the old validated result. Reject if the actual cost exceeds the confirmed budget or needs a new confirmation. Validate the entire plan before starting any sub-edit; only one construction slot may run.
4. Atomically commit the new creation state, final layout/construction plan, actual inventory changes and durable receipt. If physical validation or accounting fails, discard the successful reducer candidate, including its `applied`/`accepted` marker and local receipt. No cost or component may remain partially committed. One owner confirmation cannot silently authorize a more expensive revised plan.
5. For `acceptedHelp`, add **H +30 only**, using the current animal record; recheck compatibility, target existence, H ≤70 and the owner-wide UTC-day limit under the same transaction. Do not add owner bond or manual-care milestones, deduct owner food, or settle the donor reservation twice. The reducer reserves only synthetic donor inventory.
6. For `undoProposal`, look up `originalTransactionId` in the estate's paid-cost/component ledger. Check conflicts, legal placement for current animals and all later independent changes before restoring the proposal's differences. Refund only remaining recoverable paid cost, subtracting demolition/cancellation/earlier refunds. Do not restore normal growth, needs, bond, age, unrelated inventory, or the whole old save. If a conflict needs confirmation, discard the reducer's provisional `undone` marker until a safe plan is confirmed.

`ok:false` always has no effects. Full/daily-cap help acceptance deliberately returns a `waiting` ledger state; expiry acceptance can return an `expired` state with its one-time synthetic refund. Persist these harmless record changes even when returning the rejection message. Other validation rejections do not change owner physics or currency. `sweep` is an explicit owner/system maintenance command; it expires pending items and returns the original reservation once. Waiting gifts remain rejectable/refundable. Date limits use a fixed **UTC** day and cannot be reset by changing visitor IDs, device timezone or profile clock.

The estate adapter implements this transaction boundary in a cloned profile. It simulates every edit to completion with the shared spatial rules before committing any candidate, validates all source/target footprints and doors inside the permitted regions, checks exact cost against the selected preview estimate and maximum budget, and checks current actor routes and reachable shelter capacity. It then queues one aggregate online construction with the complete final geometry, summed duration, single cost reservation, delayed dismantling refund, and a combined construction footprint that is separately checked for temporary route safety. It records one final layout version and original transaction. Spatial validation failure returns the original profile unchanged.

The adapter's proposal undo requires the original completed transaction to remain the latest layout change, rejects active/cancelled work and intervening edits, validates current animal placement before restoration, and restores geometry at a new version. It returns at most remaining original paid cost. If the original proposal dismantled a paid facility, its completion refund is reclaimed before restoring that facility's old paid-cost ledger; insufficient current materials rejects undo. Its receipt tracks undo refunds, while the spatial module's history/receipts protect normal demolition and cancellation. No normal animal progress is restored. Help updates hunger and the technical offline-settlement baseline only, so a subsequent offline read cannot erase the benefit; care, bond and manual milestones remain unchanged.

Local visit entry/movement/interactions validate the shared graph and grant-restricted region paths. A stale scene version requires ending and re-entering the local visit rather than drawing an obsolete route on current geometry. The sample route starts on legal ground outside the initial shelter. Event records that already include `layoutVersion` retain it; older event text has only the current capture's layout context, not a claim to a recovered historical layout.

Each natural/lab profile creates its own creation state and donor ledger. A mismatched profile/owner context fails. Never transfer demo animals, resources, permissions, work authorizations or receipts to natural state.

## Future external contracts

Generation requests need authenticated owner/profile, unique request ID, permitted asset slot/region, input license references, model/prompt/asset versions, quota reservation/refund receipt, and explicit queue/generation/content-review/rule-validation/confirmation states. Returned content is an untrusted candidate. It must not carry world mutation authority. Timeouts, failures and cancellation require provider-specific known policies; the local implementation makes no latency, refund or generation-quality claim.

Real social snapshots need stable authenticated accounts, friend or named-recipient scope, snapshot version/time, allowed region/content filters, expiry and immediate revocation enforcement. Help needs a cross-account transactional donor reservation and a per-owner fixed-day acceptance counter, including atomic refund/idempotency records. Blueprint acceptance needs the owner's transaction and optimistic layout version. Public publishing and private-use/republication Remix require separate audiences, rights/provenance checks and owner confirmation; a view/edit grant cannot imply them.
