## 重要：GitHub传输使用素材分片（全部字节已包含）

GitHub文件上传通道限制大blob请求。本目录把大于2MiB的运行素材按内容去重，存入 `.asset-parts/<SHA256>/part-*`，每片最多1.5MiB。**不是外链替代素材，也不需要外站下载、密钥或原始相册。** `public/`与`dist/`同内容文件共享一套片。

GitHub初次检出时部分大GLB/音频路径尚未展开，先执行：

```bash
node RESTORE_ASSETS.mjs
```

脚本仅用Node内置模块，校验每片和完整文件SHA256，原子写回所有原路径；已有正确文件跳过。缺片/坏片会报错，不破坏该素材的已有文件。再次运行可安全补齐。拒绝路径穿越与符号链接父路径。`npm run dev`、`npm test`、`npm run build`已加pre钩子自动执行；直接静态托管dist前仍需手动执行一次。恢复后的源码/运行素材/最终dist与v14一致，额外改动只有恢复钩子和交接文件。

`SHA256SUMS.txt`描述**还原后的完整树**（包含分片），所以必须先恢复再校验；GitHub上传清单故意不上传那些待展开的大原件。请勿删除`.asset-parts`或`ASSET_PARTS.json`后再期待缺失资产能恢复。

## 1. 五分钟运行

需要 **Node.js 22.12+（或24 LTS）与 npm**；本次云端使用 Node24.22.1/npm11.9.0。无需 Tripo key、后端、数据库或私人原照片。

```bash
cd projects/avatar-dancer
npm ci
npm run dev              # Vite，终端显示访问地址
npm test                 # 全部 Node 测试
npm run build            # 静态产物写入 dist/
npx vite preview --host 0.0.0.0 --port 4173
```

已附交付时的 `dist/`，也可直接通过静态 HTTP 服务运行：

```bash
python3 -m http.server 8080 --directory dist
```

不要双击 `index.html` 用 `file://` 运行。运行资源路径以 `/assets/` 开头，默认部署在**站点根路径**；若要挂在 GitHub Pages 的 `/avatar_dancer/` 子路径，必须同时改 Vite base 与代码中的绝对素材 URL，再全测，不能只拷贝目录就认为可运行。GitHub 此文件夹只是保存工程，不等同于发布站点。

## 3. 当前人物与真正支持的流程

共 **8套造型、16个高低版GLB**：吉吉3套、LX3套、`jiaxin`（“我的分身”）黑衣白裤基础款与埃及法老2套。造型清单/模型 URL / height /旋转均以 `public/assets/characters/manifest.json` 为准。

- 角色是带真实骨骼和舞蹈的3D模型，不是静态图。标准为23骨与3个舞蹈 clip（dance_01 / dance_03 / dance_05）；骨架命名/权重是动画与镜头测试的合同。
- **吉吉最终使用原生完整旧脸、头发、后脑、颈和服装＋适配帽子。** 这是用户在发现v9破面后选择的快速稳定方案。不要重新导入v9新供体脸、剪发mask、补发束或面部嵌入试验。详见 `docs/JIJI_V10_STABLE.md`。
- LX及“我的分身”保留各自已交付模型。相似度是生成式近似，并非真人扫描；红帽较宽、部分源贴图及发片仍有生成模型限制。
- 大厅可选择换装、转圈展示、左右拖动查看。换装真正加载不同GLB，但只保持一个活动主角。
- “+我的分身”打开预置头像面板，用户点击创建后，至少等待5秒且真实GLB加载成功才解锁。并不是上传真人照片后即时建模。
- 法老提示词可编辑；演示实际支持的是预制**埃及法老**结果。成功加载后扣100**本地演示积分**；失败/取消不扣，重复回调不重复扣。未接真实支付、任意提示词生成、云账号或Tripo在线调用。详见 `docs/avatar-creation.md`。
- 当前无脸部/手指 blendshape，结尾表情氛围是姿势/镜头/特效，不是真正面部肌肉动画。

## 4. 音乐、谱面与操作

轮播顺序：**POPSTARS → FANTASTIC → UptownFunk → KILLLOVE → POPSTARS**。

| 曲目 | 时长（metadata） | BPM | 音符数 | 截取规则 |
|---|---:|---:|---:|---|
| POPSTARS | 59.348367秒 | 169.99 | 112 | 从源0开始，短于60秒 |
| FANTASTIC | 58.993565秒 | 130.03 | 112 | 从源0开始，短于60秒 |
| UptownFunk | 80.014512秒 | 115.000 | 152 | 用户明确要求整个上传音频，第3首 |
| KILLLOVE | 74.766803秒 | 131.995 | 151 | 用户明确要求整个上传音频，第4首 |

时长以解码内容/metadata为准，MP3容器padding可能略长。后两首是**明确全长例外**，不得再统一截成60秒。默认后续新曲仍从0开始、约100–120音符/60秒内，除非用户另行指定。曲名只来自附件名称，不推断艺人身份。

每首自有实际音频测得的节拍、offset和谱面，不使用随机128BPM通用谱。谱面覆盖四方向、少量双押，无三押；相关制作参数/信号验证见 `docs/GAMEPLAY_AUDIO.md` 和对应 `*-gameplay.metadata.json`。两键同时输入有独立处理，箭头键/WASD/屏幕触控均可。

成功开局才提交轮播进度；暂停不跳歌、失败加载不跳歌；大厅原粉色音乐符号可点击下一首。进度按 last-played **ID** 存储，不按索引。本地音频导入独立于默认轮播，仅在浏览器内解码，自动BPM/谱面为估测，不上传。

准备页另有轻量大厅音乐，沿用共享静音状态；Web Audio需要用户手势才能正常启动。`STAGE RUSH`原创曲保留为历史素材，不是当前默认四首之一。

## 5. 舞蹈、运镜与结果

正确输入维持连续全身舞句；偶尔miss不突然僵住，持续不输入会渐回休息。不是每个方向瞬切一个微姿势。暂停冻结动作/计时。音频时钟为判定和音乐相位基准，避免帧率积累漂移。

当前v12运镜保留150%近景基准，用真实BPM+offset驱动8拍强弱推拉，强拍约19%–22%，提前75ms启动、正拍到峰值、225ms回落；不是按键抖镜。无随机摇晃/roll。强近景可裁小腿，不能再沿用早期“始终全身安全框”的描述。`prefers-reduced-motion`减弱动态。UptownFunk使用自身115BPM及metadata offset，与其他曲目机制一致。

结算复用同一角色/同一WebGL renderer，在分数区旁展示结束动作和有限特效；不会下载另一个模特。今日本人累计为本地数据，好友排行是mock，不是联网竞赛。

## 6. 性能与状态

- 单活动主角，造型按需载入；高低版几何/骨架/舞蹈一致，仅贴图降档。
- GLB压缩字节LRU：低内存设备64MiB、常规设备128MiB。已解析资产保护当前/正在请求的模型，闲置缓存最多1项，闲置预算低内存64MiB、常规160MiB；活动/请求中的模型不计入该闲置预算，因此这不是总内存上限。具体实例配置以stage.js为准。
- 请求token防旧加载覆盖新选择；缓存不等于无内存成本。淘汰时释放几何、材质、纹理、克隆skeleton。
- DPR自适应/粗指针或低内存策略减少负载。诊断中纹理内存为RGBA+mipmap估计，非真实VRAM测量。
- localStorage保存歌曲轮播、分身解锁/积分、今日分数及部分UI状态；无服务端存档。清站点数据会重置；导出工程不包含任何玩家localStorage。
